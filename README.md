# Radiance4D

[![Windows build and test](https://github.com/ginzburg-dev/radiance4d/actions/workflows/windows_build_and_test.yaml/badge.svg?branch=main)](https://github.com/ginzburg-dev/radiance4d/actions/workflows/windows_build_and_test.yaml)
[![License](https://img.shields.io/badge/License-MIT-blue.svg)](https://opensource.org/licenses/MIT)

**A rendering engine for Gaussian splats and meshes.** Direct3D 12 and Vulkan, HLSL shaders.

1,000,000 splats at 1080p in 9.7 ms.

![INRIA train, 1.03M splats, with the per-pass overlay](docs/images/overlay.png)

---

## Why

A photogrammetry scan is a cloud of Gaussians. Everything else is triangles. Splat viewers cannot
draw models, engines treat scans as an import. This draws both.

* **Virtual production and previs.** Put CG into a scanned location and walk it live.
* **VFX layout.** A scanned environment behind a CG element instead of a flat plate.
* **Digital twins.** A scanned site with CAD or markup on top.
* **A base to build on.** The whole splatting pipeline, readable, in one repository.

The reference splatting code is CUDA, so it needs an NVIDIA card. This one is plain HLSL and runs
on any Direct3D 12 or Vulkan GPU.

---

## Gaussian splatting

A splat is an ellipsoid in space with a colour, an opacity and a rotation. Drawing a million of
them means projecting each one into a screen-space ellipse, sorting them by depth and blending
them in order. The engine does that in five compute passes and one rasterising pass.

**Culling and projection.** One thread per splat builds the 3D covariance from the scale and
rotation, pushes it through the perspective Jacobian and gets an ellipse: a centre, a radius and
the inverse covariance the pixel shader needs. Spherical-harmonic colour is evaluated here too,
once per splat rather than once per pixel. Splats whose ellipse cannot reach a pixel are dropped.

**Depth sorting.** A four-pass radix sort over the whole splat count, on the GPU. The key is the
float depth under a monotonic bit transform, so the ordering is exact rather than quantised, and
the sort is stable, so equal depths keep the same order on every run and on both backends.

**Tile binning.** The screen is cut into 16x16 tiles and every splat is paired with the tiles it
covers. The pairs are generated by walking the splats in depth order, so they come out sorted by
depth already, and a second stable radix sort over the tile id leaves each tile's list in depth
order without a second sort key.

**Tile rasterising.** One compute group owns a tile and one thread owns a pixel. Each thread walks
its tile's list from the nearest splat outwards, accumulating colour and transmittance, and stops
as soon as the pixel can no longer change. That early exit is what binning buys: a back-to-front
blend has to touch every splat covering the pixel, this one usually touches a fraction of them.

The result is composited over the mesh image. Splats behind geometry are rejected per splat against
the depth the mesh pass wrote, so a scan and a model occlude each other correctly.

## Datasets

`.ply` files from the reference 3D Gaussian Splatting implementation load directly, with
degree-3 spherical harmonics, log scales, sigmoid opacity and `wxyz` quaternions converted on
read. COLMAP trains in a right-handed, y-down world and the engine is left-handed and y-up, so the
loader mirrors the scene: positions, the rotation quaternion and the six harmonic bands that are
odd in y.

Verified on INRIA's pre-trained scenes: `train` at 1,026,508 splats and `truck` at 2,541,226.

```
radiance4d_viewer.exe --splat-ply point_cloud.ply
```

A reconstruction leaves sparse low-opacity splats far outside the subject, so the camera frames on
the median position and the distance half the splats are within, not on the bounding sphere. On
`train` that is a radius of 2.4 against the bounds' 145.

## Reconstruction tooling

`tools/reconstruct` reads a COLMAP sparse model and writes its points as a `.ply` the engine
renders. Pure Python, no dependencies.

```
python -m r4drecon inspect <sparse-model-folder>
python -m r4drecon export  <sparse-model-folder> out.ply
```

Each point becomes a splat with its colour, a starting opacity and an isotropic scale taken from
the distance to its three nearest neighbours, which is the initialisation the reference
implementation optimises from. The neighbour search goes through a uniform grid, so it stays linear
in the point count: 28,000 points take about 8 seconds.

See [tools/reconstruct/README.md](tools/reconstruct/README.md).

## Performance

INRIA's `train`, 1,026,508 splats at spherical-harmonic degree 3, at 1920x1080. RTX 3080 Laptop
GPU, driver 617.14, i7-11800H, RelWithDebInfo, vsync off, mean of 200 measured frames after a
warm-up.

| Pass | D3D12 | Vulkan |
|---|---|---|
| Cull | 0.91 ms | 0.74 ms |
| Depth sort | 0.81 ms | 0.74 ms |
| Binning | 1.38 ms | 1.27 ms |
| Tile sort | 2.74 ms | 4.00 ms |
| Rasterise | 3.82 ms | 3.59 ms |
| Composite | 0.04 ms | 0.04 ms |
| **Frame** | **9.70 ms** | **10.38 ms** |

The same scene cost 96 ms with the sort on the CPU. The GPU radix sort, the compute cull pass and
the tiled rasteriser took it to under ten.

Timestamps bracket each pass on both backends, and the six scopes account for the frame to within
0.01 ms. The overlay shows the same breakdown live, and `--benchmark <n>` reports it after a
warm-up with the debug layer off.

[docs/RENDERING.md](docs/RENDERING.md) has the pipeline in detail and what every change measured.

## Rendering

Meshes are shaded with Cook-Torrance GGX: base colour, metallic-roughness, normal and emissive
maps from glTF 2.0, three analytic lights, a 2048 shadow map with 3x3 PCF, and image-based
lighting from a procedural sky with a cosine-convolved irradiance map. Tone mapping is ACES with
an exposure control.

![Material grid](docs/images/material-grid.png)

Both backends draw this from the same HLSL. One vendored DXC compiles every shader to DXIL for
Direct3D 12 and SPIR-V for Vulkan at build time.

The D3D12 backend uses Enhanced Barriers, the retail Agility SDK, explicit adapter selection, DRED
breadcrumbs and a counted validation message callback. The Vulkan backend uses dynamic rendering
and synchronization2.

## Testing

```
ctest --preset windows-d3d12-debug
```

Unit tests for the maths, the `.ply` parsing and the reconstruction tooling. Device tests run on
WARP, Microsoft's software rasteriser, so the whole splatting pipeline is exercised with no GPU
present and CI can run it on a hosted runner. Image regression compares renders against stored
references with documented tolerances. A parity test holds Direct3D 12 and Vulkan to the same
image, currently within 1 of 255 per channel.

`make check` runs the formatting check, the build and the tests, which is what CI runs.

## Building

Windows 11, Visual Studio 2022 (v143), CMake 3.26+, a D3D12 GPU. Dependencies are fetched and
hash-pinned by CMake, nothing is installed system-wide.

```
cmake --preset windows-d3d12
cmake --build --preset windows-d3d12-debug
ctest --preset windows-d3d12-debug
```

See [docs/BUILDING.md](docs/BUILDING.md).

## Running

Load a scan or a model:

```
radiance4d_viewer.exe --splat-ply point_cloud.ply
radiance4d_viewer.exe --scene model.gltf --splats 2000
radiance4d_viewer.exe --backend vulkan
```

Mouse orbits, pans and zooms. WASDQE in free-fly. F1 vsync, F2 camera mode, Esc quits.
`--help` lists every flag.

Render without a window, and without a GPU:

```
radiance4d_viewer.exe --headless --frames 30 --out frame.png
radiance4d_viewer.exe --splat-ply point_cloud.ply --benchmark 200
```
